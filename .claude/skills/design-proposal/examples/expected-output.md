# design-proposal 期待出力例

## ケース1: 良い例（OK）

### 状況
「お気に入り動画にメモを複数件つけられるようにしたい。今は1件固定」という相談を受けた。

### 期待出力

```
## 設計提案

### 前提確認
- 現状: FavoriteVideoMemoTransaction は1動画につき1件のメモを想定した構造
- 目的: 1動画に複数件のメモを付けられるようにしたい

### 案A: 既存テーブルのまま複数行を許容する
概要: FavoriteVideoMemoTransaction の一意制約（userId, videoId）を外し、メモIDを別途採番して複数行を許容する
メリット: 新規テーブル不要、既存カラムをそのまま使える
デメリット: 「最新のメモ」を特定するロジックが別途必要になる
実装コスト: 低

### 案B: メモ専用の子テーブルに分離する
概要: FavoriteVideoMemoTransaction を「動画に対するメモの入れ物」の集約とし、メモ本文は新規の子テーブルに分離する
メリット: メモの追加・削除・並び替えが自然にモデル化できる
デメリット: テーブル追加・マイグレーション・Repository新設のコストがかかる
実装コスト: 中

### 推奨案: 案B
選定理由: 「複数件」を将来的に編集・削除・並び替えまで求められる可能性が高く、案Aの制約解除だけでは早期に破綻しやすい。今の時点でコストを払っても集約を分離した方がメンテナンス性が高い。

### 破綻ケース
- メモに既読・ピン留めなど動画をまたいだ集計が必要になった場合、子テーブル側にさらに属性を足すことになり再設計が必要になる

### 次のステップ
- impl-planner に「案B・子テーブル分離」を前提として引き継ぐ
```
